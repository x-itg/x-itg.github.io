信任黑箱：AI时代，我们如何重新建立可控的确定性？

黑箱无法消除，但可以被管理。信任无法绝对，但可以被可控。

itg · 公众号: 火星火箭 · 工程心法

软件的底层公式

我做嵌入式开发、AI工程落地这么久，始终笃定一句话：软件的底层公式，几十年从未变过。

永远是：输入 → 规则 → 输出。

用户提供数据，系统执行既定逻辑，最终反馈确定结果。早年我写嵌入式固件、工控上位机代码，整套逻辑极度直白：需求落地为逐条 if-else、固定分支、明确时序逻辑。每一条规则都可见、可审查、可追溯。

程序出Bug，不需要猜。通过Git版本追溯、日志打点、时序复现，总能精准定位到具体代码行。修复、验证、上线，形成完整闭环收敛。

那个时代，我们对软件的信任，来源于透明和确定。规则是人写的、固定的、不变的，输入一致，输出必然一致。

但大模型时代，这套稳定体系彻底被打破。

传统代码

人逐条定义规则，机器严格执行。没有固定代码分支之外的逻辑，执行链路完全可追溯。

不确定性来源：人的书写疏漏。

大模型

模型自主归纳逻辑、自主匹配规则、自主生成输出。没有固定代码分支、没有明文逻辑、没有可追溯的执行链路。

不确定性来源：模型自主演化的不可观测性。

同样的需求输入、同样的资料投喂，今天输出精准可用，明天大概率逻辑跑偏。你看不到它的推理路径，不知道它采信了哪些信息、忽略了哪些约束、变更了哪些隐性规则。

它把效率拉满的同时，也给自己封成了一个绝对的信任黑箱。

窗口越大，失控成本越高

很多人迷信大模型超大窗口能力，动辄调侃："现在百万上下文窗口，把整套项目源码、需求文档、设计规范全塞进去，不就一劳永逸？"

从业落地多年，我的答案始终很坚定：窗口能装得下，不代表系统能用得好。

行业普遍存在一个认知误区：上下文窗口越大，模型准确度越高。但在真实工程落地中，长上下文带来的最大问题，是信息噪声泛滥与关键信息沉没，也就是工程里典型的「上下文腐化」。

这和我体系里的负日志逻辑高度契合：大量本不该出现的错误、本不该遗漏的关键约束，在大模型长上下文场景下呈指数级爆发。传统软件开发，错误可复现、可定位、可收敛；大模型长上下文场景，很多错误随机出现、无固定规律、无法提前规避。

业内经典的「中间信息丢失（Lost in the Middle）」现象，更是所有AI开发者的常态：模型对对话开头的指令约束、结尾的新鲜输入高度敏感，但对中段密密麻麻的核心参数、硬性约束、边界条件，极易自动过滤遗漏。

我做工控AI项目深有体会：把整套设备协议、校准规范、通讯帧格式全部喂进上下文，模型依然会忽略关键时序约束、漏掉必填校验位。不是它没读到，是海量噪声稀释了核心信息。

更核心的问题，是我一直强调的闭环失效：

传统工程闭环

人工写规则 → 机器执行 → 人工验证修复。双向可控。

AI的伪闭环

模型自主定规则、自主执行、自主校验。我们只能看到最终输出，完全观测不到中间推理状态。

你以为系统已经收敛稳定，实则模型大概率收敛到了一套自洽但不符合业务规范的私有逻辑。这种看不见的偏差，就是信任黑箱的根源：确定性彻底消失，信任从"有据可依"，变成了"被动赌博"。

Context Engineering，是黑箱的唯一透明外壳

很多人把提示词工程与上下文工程混为一谈，在我的工程体系里，二者边界极其清晰：

Prompt Engineering

= 定义指令规则

告诉模型：任务目标、输出格式、角色约束、行为边界。是静态规则定义。

类比：工控系统的固件底层配置。

Context Engineering

= 管理内存环境

控制每一轮模型调用：该加载什么、淘汰什么、挂载什么、压缩什么。是动态资源调度。

类比：工控系统的实时内存与数据流调度。

简单来说：Prompt 决定模型"该做什么"，Context 决定模型"能做好什么"。模型能力再强，上下文混乱、信息残缺、噪声过载，最终输出必然失控。

这也是我落地AI项目的核心架构思路，整套体系分为四大可控模块：

System 层

1. 静态基线规则

固化项目全局约束，对应 .cursorrules、架构规范、业务红线。永久生效、不随对话迭代变更，是模型行为的底层边界，杜绝根本性逻辑跑偏。

User 层

2. 动态业务输入

清洗每一轮真实业务输入，剔除无效话术、重复信息、冗余描述，保证输入数据流干净无噪声。

Memory 层

3. 分层记忆调度

短期做滑动窗口淘汰，避免上下文臃肿；长期通过文件存储、KV索引、结构化笔记留存核心架构决策、Bug记录、边界参数，避免重复踩坑。

RAG/Tools 层

4. 工具与检索可控挂载

不盲目全量检索、不随意挂载工具。根据任务类型，精准调取Top-K核心资料、匹配对应工具集，杜绝无效检索带来的信息污染。

上下文质量，决定人与AI的共生演化高度

我一直提出「人与AI共生演化」的核心观点：AI的输出质量，从来不是模型单方面决定的，而是由人类投喂的上下文质量决定的。

我拿自己嵌入式固件开发场景举一个最真实的落地对比：

场景一：裸模型调用

仅输入一句需求："帮我优化ESP32-P4设备的串口通讯逻辑，修复丢包问题。"

没有硬件原理图、没有原有通讯协议、没有波特率参数、没有报错日志、没有时序约束。

结果：通用模板代码，无法适配硬件版型，解决不了特异性丢包问题。

场景二：结构化精准上下文

通过上下文组装服务，自动挂载：设备硬件参数、历史3次丢包Bug记录、工业串口固定约束、串口日志解析工具、仅优化通讯容错的精准指令。

结果：精准匹配硬件、贴合工程场景、规避历史问题、符合业务约束。

模型没变，变的是上下文的可控性。
一味追求更高配模型、更大窗口，却忽略了上下文结构化，才是AI落地的核心护城河。

Context Assembler：用决策切换终结"每次从零验证"

很多开发者都会陷入一种内耗：每一次模型调用，都要手动梳理资料、手动调整prompt、手动筛选历史、手动排查错误。明知低效，却不得不做，因为AI没有稳定规则，每一次输出都是全新随机态。

这恰好印证了我的决策切换法则：成熟的工程体系，必须固定流程、动态换参，杜绝每次重新决策、重新试错。

为此我在个人项目中，落地了一套 Context Assembler 上下文自动组装服务，彻底解决黑箱不可控问题。这套服务只做一件事：在模型推理之前，用固定工程流程，替代人工随机组装。

固定执行链路（7步）
  1. 通过会话ID拉取压缩后的核心历史摘要，摒弃冗余对话
  2. 根据当前任务类型，自动加载专属静态规则模板
  3. 按需执行精准RAG检索，只留存Top-K高关联核心资料
  4. 匹配任务场景，精准挂载对应工具集，杜绝工具泛滥
  5. 按优先级排序：系统约束 > 任务目标 > 核心证据 > 工具规则 > 历史摘要
  6. Token预算校验，分级压缩冗余信息，保留核心业务数据
  7. 输出标准化、结构化、可追溯的完整上下文
流程永久固定，唯一变量是业务参数。同时我搭建了专属工程评测集，沉淀50+真实嵌入式、软件开发场景用例。每一次迭代优化组装规则，都要全量跑一遍评测集，用数据验证稳定性。这正是负日志体系的正向应用：把所有遗漏、失真、误判的失败案例沉淀下来，反向迭代优化上下文组装规则，让系统持续闭环收敛。

长任务落地：三种工程方案破解上下文腐化

面对长时间、多轮次、高复杂度的开发任务，单一的上下文组装服务不足以支撑全程稳定，长期运行必然出现信息冗余、过期结论、无效数据堆积。

我在实战中沉淀了三套分层解决方案，全覆盖长周期AI任务：

📦

上下文压缩 Compaction

窗口临近饱和时，自动摘要归档：保留架构决策、未解决Bug、核心参数，丢弃冗余工具日志、过期调试信息，轻量化重启对话窗口。

📝

结构化外置存档

让AI将每一轮核心进展、决策结论、待办事项，自动写入 NOTES.md 结构化文档。窗口重置后，通过读取外置笔记延续进度。

🔀

子Agent拆分

主Agent统筹，子Agent负责专项检索、调试、编码。子Agent只向主Agent输出高密度结论，不传输原始冗余数据，保证顶层上下文极度干净。

AI上下文工程，最容易踩的四类致命坑

结合大量落地负日志复盘，总结四个高频翻车点：

坑一：工具边界模糊

很多人写工具描述只求详细，不定义边界。合格的工具文档，必须明确：适用场景、禁用场景、参数范例、副作用约束。边界模糊，必然导致模型乱调用、错调用。

坑二：检索结果裸投喂

RAG检索后直接全量塞入上下文，不裁剪、不摘要、不筛选。海量原始日志、冗余文档淹没核心信息，直接引发上下文腐化。需保留关键溯源信息，精简无效内容。

坑三：少样本示例泛滥

堆砌几十条边缘案例，试图覆盖所有场景。最终模型过度拟合示例表面格式，忽略底层业务逻辑。3-5个典型标杆案例，远胜百条冗余特例。

坑四：无降级兜底策略

未设计失败分支：检索无结果、工具超时、摘要丢失、多工具冲突时无预案。工程化落地，无兜底的设计，就是最大的设计缺陷。

真正的信任，不靠赌，靠可控

回到文章最初的软件公式：输入、规则、输出。

没变的是公式，变的是规则的定义者。从前是人定规则、机器执行，全程透明可控；现在是人机协同定规则、模型自主执行，全程黑箱未知。

所有人对AI的不信任，本质不是不信任模型能力，而是不信任这份永恒的不确定性。

但Context Engineering的价值，就是在绝对的黑箱里，人工搭建一层透明的工程外壳。我们不再被动等待模型输出结果，而是前置控制输入环境、结构化数据流、标准化推理边界。出问题不再盲目试错，而是可回溯、可定位、可迭代、可收敛。

这也像我写亲密关系时悟出的道理：真正的信任，从来不是无条件的盲从。真正的信任，是明知它会出错，但我有完整的体系，修正错误、规避风险、持续优化。
AI时代的确定性，早已不在模型本身。
而在我们人为搭建的、层层约束、闭环迭代、持续收敛的工程体系里。

黑箱无法消除，但可以被管理。
信任无法绝对，但可以被可控。

控制你能控制的，验证你不能控制的。
这，就是我们对抗AI不确定性的终极解法。
